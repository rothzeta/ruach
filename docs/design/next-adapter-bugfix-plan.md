## C2: conditional, thin non-Coordinator adapter

### Need and capability gate

C2-I opens only for a named consumer need: for example, the owner requests a second-harness advisory diagnosis of the real C3 defect's competing causes, with a reason that the currently supported route does not cover. Merely wanting another supported brand is insufficient. Record advisory question, owner, selected existing role, permitted repository reads/output, route/model declaration, native resource permissions, cost/turn bound and why this adapter is useful. C3 and the peer's other features proceed without C2 when that need is absent.

A Scout investigates capability first. Required evidence is a functioning installed version, pinned executable identity, exact help/primary-doc support and a bounded no-model preparation proof. Do not emit production argv, even in a supposedly illustrative dry-run, for an unproven mechanism. The investigation reports each required capability as proven, absent or unknown:

1. Add only the canonical role instructions to the existing native instructions. Preserve project/personal/plugin customization, native trust and account behavior. A native subagent file or replacing the main system prompt is not equivalent. If additive delivery cannot be demonstrated, retain unsupported_adapter.
2. Verify role identity/hash and canonical resource discovery at the actual source and new worktree cwd. Workers may discover descriptions but must not load workflow bodies; no body is inserted by the launcher. Where a documented per-launch exclusion exists, prove its scope without suppressing unrelated skills. Unknown account/cache visibility is reported rather than claimed absent.
3. Establish current model/effort and any minimum native flags from the actual version. No arbitrary native pass-through or guessed flag is introduced. Validate incompatible values before launch writes, using existing exit/diagnostic contracts.
4. Determine whether read-only inspection itself initializes native runtime assets. Enumerate necessary writes and obtain their scoped authorization before invoking it. Do not replace HOME, credentials, trust files, project settings or global defaults. Missing trust/account interaction is awaiting-input, never an invitation to automate a dialog.
5. Prove interactive Herdr readiness, separate assignment submission and safe quoting/path delivery. Headless output support alone is insufficient. Help/model names do not establish entitlement or readiness during a real turn.

C2-A can be assigned only after the capability report and consumer need are accepted. If native syntax or additive semantics remains unknown, close C2-I with a specific hold and no launcher implementation. A supported existing harness remains an owner-selected alternative, not an automatic route change.

### Minimal implementation once proven

Implement the existing Plan contract in agy.ts, using current helper functions and private temporary material only when the proven native mechanism requires it. Reject the Coordinator before native inspection/materialization; every other role still requires a consumer-declared route and a valid canonical role file. Initial acceptance covers the named advisory role. It does not certify every non-Coordinator role's write behavior merely because preparation is generic. A later Implementer/native-writing claim needs its own bounded smoke.

Keep --permissions inherit; unmapped auto-review remains an unsupported_permissions failure before native inspection or resource creation. The development wrapper defaults to auto-review, so an authorized C2 launch through it must explicitly select --permissions inherit; do not change its default or silently downgrade a request. Never map auto-review to skip/bypass/unconditional approval. A future verified mapping is a separately reviewed amendment, not part of this minimum. Do not alter consumer role/model allowlists or active development routes.

Use the existing linked-worktree launch and second preparation in the resulting checkout. Invalidate capability proof when executable, version, cwd configuration, role hash or relevant discovery differs. Existing readiness uncertainty keeps named resources and reports actual state; it never repeats startup. Missing linked-parent context holds the linked acceptance row; standalone fallback is separately reported and cannot prove linked launch.

Role delivery and assignment remain separate. The Coordinator sends a short assignment identifying a large UTF-8 brief by absolute path in the worker checkout or an explicitly readable consumer scratch area. Preserve newlines, spaces, Unicode and shell-looking text through structured argv/text, without shell interpolation. No invented prompt-file flag is needed: verified assignment delivery can instruct the worker to read the file. Do not echo the full brief into diagnostics. The role must be in force before the assignment; no paid turn is required for a preparation fixture.

Review the adapter code and failure tests before authorizing the single native advisory smoke. Its evidence names actual native/Herdr versions, role hash, cwd/worktree identity, configured route and permission mode, discovered technical skill, assignment/brief path, original native instruction marker, actual ready/waiting state, durable advisory answer and validated handoff. Consumer authority and applicable workflow exclusion are tested with a realistic conflict, not assumed from a fake argv. Advisory usefulness requires a bounded supported hypothesis or discriminating check, not a native success banner. Missing access/entitlement/config proof is a held acceptance row.

## C3: debugging skill and bugfix workflow

### Separate responsibilities

ruach-debugging is an instruction-only technical skill for investigation and correction by the applicable existing worker. It triggers on a reported known defect or observable unexpected behavior. It does not orchestrate workers, merge, deliver, choose models or establish consumer authority. A Scout can use its investigative portion and report findings; only an authorized Implementer changes source. Keep its main instructions concise and put decision-changing evidence guidance in one reference.

ruach-workflow-bugfix is a Coordinator-only instruction resource. It selects the proportionate path, supplies the intended behavior and exact scopes, resolves authority and conflicting findings, sequences required checks/review/delivery, and closes the task record. It uses debugging guidance in worker assignments; it does not copy its technical checklist into a second editable source. It does not force a council, Architect, Tester or new service for every defect.

Only the Coordinator loads existing or candidate workflow bodies for compatibility inspection/use. The future Implementer authors the assigned new workflow from this self-contained contract without loading other workflow bodies. Reviewer source inspection covers technical skill/code, workflow metadata, notices and packaging; Coordinator supplies a separate compatibility observation for the workflow body. Independent review of consequential workflow behavior grades actual isolated Coordinator outputs/traces against the consumer assignment and rubric. It must not pretend metadata inspection is workflow-body review or assign the Coordinator the Reviewer's technical acceptance work.

### Debugging evidence and sequence

The skill records a compact defect evidence chain:

1. State intended observable behavior and its authority: user contract, documented API or accepted requirement. Separate a defect from an unsupported feature request, an environment failure and an ambiguous expectation. Request the missing decision through the responsible owner while continuing independent investigation.
2. Preserve the original failing command/input, cwd, version/commit, relevant permissions/environment, actual versus expected result, and raw output location. Reproduce on the named supported baseline with bounded diagnostics. Sensitive data stays out of committed fixtures. A denied socket, SIGILL or wrong revision is not proof of a product defect.
3. List only plausible causes supported by observations. Run the cheapest discriminating check that can refute the leading explanation. Record mechanism and evidence before prescribing a fix. If reproduction is unavailable, say what remains unknown; do not report a guessed cause as established.
4. Correct the narrow cause within assigned files and preserve neighboring public behavior. If investigation discovers required files or a changed intended contract outside scope, report a concrete scope/decision amendment before changing them. Do not redesign adjacent systems, relax permissions or delete/soften tests to obtain a green run.
5. Add a feasible meaningful regression at the public boundary. Establish failure on the actual unfixed version and success on the candidate when possible; otherwise document the precise limitation and obtain review of adequate alternative evidence. Keep valid controls and invariants. Tests should capture the failed contract, not mirror private implementation or assert prose wording.
6. Repeat the original reported failure with the corrected candidate and comparable environment/input, in addition to the regression and required affected checks. Preserve actual outputs. A new unit test passing cannot replace that retest.
7. Return exact source/test/review/delivery revisions and command exit evidence under the existing handoff contract. Required independent review and authorized delivery remain separate. Failed review yields a bounded correction and new exact-candidate review, not self-approval.

Direct: one small local defect with clear authority, limited files and a known reproduction can be handled by an authorized Implementer; consumer-required review and delivery still apply. Compact: Coordinator assigns Implementer and independent Reviewer, adding a short investigation only if necessary. Full: use Scout when cause is unresolved and optional Architect for consequential interface/design choices; add integration or user-facing verification only when the defect warrants them. Consumer policy overrides these defaults. Two failed diagnostic/correction cycles trigger an owner checkpoint by default; this is a proposed consumer-adjustable escalation threshold, distinct from R7 command retry/flake policy and this planning batch's five-round agreement limit.

The Coordinator's record carries R3 proposition/decision IDs, owner dispositions, accepted scope changes, original reproduction pointer and stable report IDs. Observed reports are not handled outcomes until the Coordinator durably records disposition. Native resume does not imply accepted changes or authorize new work.

### Real defect selection and interfaces

The later C3-S demonstration chooses one actual owner-reported or currently observed small defect with a supported intended contract, reproducible failure on an identified revision, feasible public regression and bounded few-file correction. Record the source of the report and confirm it still fails; historical already-fixed inventory entries do not qualify. Prefer a consumer project or a separately authorized Ruach issue that does not collide with R1–R7 or peer implementation ownership. Do not treat the local agy CPU crash as a Ruach bug, assume an unresolved hosted issue's cause, introduce an intentional defect and label it real, or reuse the example date bug as completed evidence.

A Scout selection report proposes the exact affected files, checks, input/environment and real issue provenance. The Coordinator accepts that scope and delivers a filled Implementer assignment before source changes. No eligible reproducible defect means the real demonstration is held; synthetic packet controls can still be prepared. The actual correction uses the sequence above, independent Reviewer, original failure retest and separately authorized delivery. Hosted/native requirements must be declared for this specific issue rather than inherited from an unrelated prior task.

Proposed peer interface, pending actual review: C1 supplies a durable scoped decision/council result when needed; C3 consumes accepted intended behavior and resolved design decisions without requiring a council for a small fix. C4 receives exact build/revision, user-visible acceptance, reproduction instructions and allowed resources; a QA finding feeds a C3 issue, and QA retests the corrected exact build. C5 may demonstrate the accepted chain on its two real project workflows; this C3-S defect alone does not satisfy C5's wider evidence. C2 is optional advisory diversity for a named question, never a prerequisite for C1/C3/C4/C5 on supported routes. No peer positions or packaging are presumed accepted in this first-round plan.
