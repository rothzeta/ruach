# 0.3 design: recoverable installation and readiness

Status: proposed (Architect, task 0.3-arch). Scope: roadmap Track A5 (RU-07, RU-08, RU-09) and Track C item 2. Items marked **needs-decision** need user approval before they are implemented.

## Part 1: recoverable snapshot installation (A5)

### Current code paths

Ruach owns only one installation writer: `scripts/install.ts`, which is installed into consumers as `ruach-install.ts`. Its `install` and `check` subcommands handle first install, update (`--version`/`--revision` over an existing `ruach.json`), adoption (`--replace`) and integrity checks. The other routes hand writing to external tools: `just install` runs `bun install --frozen-lockfile` per skill, `just install-global` runs the Skills CLI, and `just install-plugin` runs `claude plugin`. A5 does not change those routes. The Herdr launcher writes only a private `mkdtemp` directory and Git worktrees, and neither is a snapshot.

`install()` currently works in this order:
1. Read the committed tree.
2. Load the old manifest.
3. Compute drift over old managed skills.
4. Check conflicts.
5. `unlinkSync` the removals.
6. `writeFileSync` and `chmodSync` each file in place.
7. `writeFileSync` the `ruach.json` file in place.
8. Print success.

### Failure modes

| Finding | Defect in current code | Consequence |
| --- | --- | --- |
| RU-07 | Removals and writes happen in place, one at a time, with no journal. The metadata is written last, but other failures can occur first: an I/O error, a permission error, `ENOSPC`, a directory standing where a file is expected (`mkdirSync`/`writeFileSync` throws), or a signal. | A mix of old and new files is left on disk, some removed files are lost, and the old manifest remains. No rollback exists, and the only way back is a re-run with `--replace`. |
| RU-08 | `writeFileSync(path)` opens the existing inode and truncates it. `chmodSync(path)` also changes that inode. | If a managed file is hardlinked to a file outside the snapshot (for example via `cp -l`, a dedup tool or a backup), the outside copy is overwritten and its mode is changed. |
| RU-09 | `drift()` and the conflict check only walk skill roots listed in the **old** manifest. An incoming skill whose folder already exists (left by an interrupted install, a manual copy or another installer) is never walked. | Install "succeeds", and then the next `check` fails on unrecorded files. Leftover content sits inside a Ruach-named skill that a harness may load. |
| RU-09 | Nothing verifies the result after writing. | Success is printed even when the tree does not match the manifest. Possible causes include a case-insensitive filesystem collision, a concurrent writer, or truncation. |

### Chosen design: per-path staged rename with a journal and rollback

1. **Staging directory and lock.** Create the target directory if needed, then call `mkdirSync(target/.ruach-staging)` once, without `recursive`. This is an exclusive create, so it serves as both the concurrency lock and the marker of an interrupted install. The staging directory sits beside the managed trees, so renames normally stay on one filesystem. It is not under `skills/`, so the skill walk never sees it, and `destination()` cannot produce that path.
2. **Never write through an existing path.** Write each incoming file as `.ruach-staging/new/<index>` with `flag: 'wx'` and its final mode, then `renameSync` it onto the destination. Before replacing or removing a destination, rename the old entry to `.ruach-staging/old/<index>`. A rename moves directory entries and never opens the inode, so any outside hardlink keeps its content and mode (RU-08). This removes every in-place `writeFileSync`, `chmodSync` and `unlinkSync` on managed paths.
3. **Journal.** Before the first rename, write the planned operations (index, relative destination, and kind: create, replace or remove) to `.ruach-staging/journal.json`. During the commit, keep an in-memory list of completed steps. For each file this run creates, also record its `dev`/`ino`.
4. **Commit point.** `ruach.json` is replaced last by the same staged rename. Remove `.ruach-staging` (and its backups) only **after** the immediate integrity check passes. A process that dies before that point leaves a recoverable staging directory.

**Rejected alternatives:**
- **Swapping whole `skills/<name>` or `.agents` directories.** The target mixes Ruach files with consumer policy, extra skills and per-skill `node_modules`. A directory swap would lose or have to copy those, and it would still need a merge.
- **Copying the old tree to a backup before writing in place.** This doubles the I/O and still writes through hardlinks.
- **Refusing destinations with `nlink > 1`.** The rename approach makes them safe, and refusing would block valid installations.
- **A temporary file per destination directory.** It would leave stray files inside skill roots after a crash, and those would show up as drift.

### Step ordering

All steps up to the commit phase are read-only:

1. Parse the arguments, read the committed tree and check the version (unchanged).
2. Refuse if `target/.ruach-staging` exists. Also refuse if the metadata is a symlink (unchanged).
3. Load the old manifest. Compute drift over the **union** of old and incoming managed skill roots (RU-09 preflight).
   - In incoming roots, a regular file outside the incoming set and outside the ignored names (`node_modules`, `__pycache__`, `*.pyc`) is a leftover.
   - Without `--replace`, any drift or leftover fails before writes, as drift does today.
   - With `--replace`, regular-file leftovers become removals.
   - A non-regular entry (symlink, FIFO, socket, or a directory where a file is expected) fails even with `--replace`. Ruach never removes what it cannot back up as a plain file, so manual cleanup is required.
4. Check conflicts and validate removals (unchanged). Make sure every destination's parent chain has no symlinks (unchanged). Also make sure that no destination is a directory and no needed parent directory is a file, so these structural failures surface before mutation.
5. Run `mkdir target` (recursive), then `mkdir .ruach-staging` (exclusive). Write all staged files and the journal. A failure here removes only the staging directory, and the target is otherwise untouched.
6. Commit phase, in deterministic sorted order:
   1. Create missing parent directories and record them.
   2. For each removal or replacement, rename the old entry to `old/<i>`.
   3. For each create or replacement, rename `new/<i>` onto the destination.
   4. Rename the staged `ruach.json` (backing up the old one first).
7. Run the integrity check: `load(target)` and `drift(target, manifest)` over the union of roots, and confirm the loaded manifest equals the intended one byte for byte. If anything fails, roll back.
8. Run `rmSync(.ruach-staging, { recursive: true })` and print success. If deleting the staging directory fails, still exit 0, but warn and name the path. The tree is already verified, so the next run will refuse until the user removes the directory, and the warning says this.

### Rollback bounds

Rollback runs after a failure in step 6 or step 7:
- Steps are reversed in reverse order:
  - Unlink a file this run created, but only if its `dev`/`ino` still matches the recorded value.
  - Rename `old/<i>` back to its destination.
  - Remove (`rmdirSync`) recorded created directories, only if they are empty.
- It touches only paths listed in this run's journal. It never deletes recursively outside `.ruach-staging`, never follows symlinks, and never retries. Each step is attempted once, and work continues past individual failures so the problems can be reported.
- **Full success:** the target is restored byte for byte, including the old `ruach.json`. The staging directory is removed, and the process exits 1 (no change).
- **Partial failure:** the staging directory is kept with its journal and backups. The process names the failed paths and exits with a **new code 3** ("rollback incomplete; manual recovery needed"). Codes 0 and 1 keep their current meaning. Code 3 is an additive contract change and must be documented in the README and `docs/operations.md`.
- **Crash or SIGKILL:** the staging directory is kept. The next `install` refuses with a pointer to it, and `check` reports `interrupted install: .ruach-staging present` as a failure. Manual recovery means restoring `old/*` per `journal.json`, or removing the staging directory and running `install --replace`. **needs-decision:** whether 0.3 should add an `install --recover` that replays the rollback from the journal. Recommendation: defer it, and keep the documented manual path. This adds no new command surface.

Durability: `rename` is atomic for each path. Ruach does not fsync each file. A power loss is detected by `check` (hash drift), and recovery is done with `--replace`.

### Regression tests to write first

These go in `tests/install.test.ts`. Each one drives only the CLI and asserts on observable tree and exit-code behavior. Shared helpers:
- After every successful install, assert that `target/.ruach-staging` is absent and `check --source` passes. This becomes the RU-09 "immediate integrity" assertion across the whole suite.
- A `treeHash(target)` helper that records paths, contents, modes and inode numbers, used for "no change" assertions.

1. **Hardlink update (RU-08).** Install, then `linkSync` a managed file to `base/outside`. Change it in the source and install the new commit. Expect the outside file's content, mode and inode to be unchanged, and the destination to have new content on a different inode.
2. **Hardlink plus mode change (RU-08).** Toggle an executable bit in the source. The outside link's mode stays the same.
3. **Hardlink removal and `--replace` adoption (RU-08).** The source drops a hardlinked managed file, so it is pruned. Also cover the case where an unmanaged conflicting destination is hardlinked outside and adopted with `--replace`. In both cases the outside content is unchanged.
4. **Commit failure rolls back (RU-07).** Make one later destination directory read-only (`chmod 0555`; skip when uid is 0). Install an update that changes files both before and inside that directory. Expect exit 1 and an identical `treeHash`, including `ruach.json`, with no `.ruach-staging`. A follow-up `check` passes.
5. **Removal is restored on rollback (RU-07).** The same setup as test 4, where the update also prunes a file. The pruned file is restored.
6. **New directories are cleaned up (RU-07).** The update adds a new skill, and the commit then fails. The new skill directory does not remain.
7. **Leftover in an incoming root, without `--replace` (RU-09).** The source adds `skills/ruach-new`, and the target already has `skills/ruach-new/stale.md`. Expect exit 1 with no change.
8. **Leftover in an incoming root, with `--replace` (RU-09).** Under the same setup, `--replace` succeeds, `stale.md` is gone and `check` passes.
9. **Dependencies are not leftovers (RU-09).** An incoming root that holds `node_modules/x` installs without `--replace`, and the dependency is kept.
10. **Non-regular leftover (RU-09).** A symlink, and a FIFO where the platform supports one, in an incoming root fails even with `--replace`, with no change.
11. **Interrupted install.** If `target/.ruach-staging` exists, `install` exits 1 with no change, and `check` exits 1 and names the staging directory.
12. **Structural conflict caught in preflight (RU-07).** A directory exists where an incoming file is expected. Expect exit 1 with no change, even with `--replace`.

The existing tests stay as they are, and they must keep passing.

Known gap: the rollback path in step 7 (integrity failure after a successful commit) cannot be triggered on Linux without a fault-injection seam. It shares the rollback code with tests 4–6. Recommendation: do not add a test-only environment hook. Record the gap in the Implementer handoff.

## Part 2: readiness command (Track C2)

### Name and placement

The command is a new **`ready` subcommand of the existing installer script**:
- In a consumer snapshot: `bun .agents/ruach-install.ts ready [--route skill|native|herdr] [--json]`.
- In a source checkout: `bun scripts/install.ts ready …`, with `just ready *args` as a thin source-development recipe.

Reasons:
- The installer script already ships in the source checkout, in the plugin directory (the plugin source is the repo root `./`) and in every snapshot.
- It reuses `load`/`drift`/version logic.
- It needs no package dependencies, which matches the root-tools rule.

**Rejected alternatives:**
- **A Just recipe only.** Recipes are not copied into consumers.
- **A script inside `ruach-herdr`.** This couples readiness for every route to the Herdr skill and its nested dependencies, which may themselves be missing.
- **A new `ruach-setup` skill.** This adds a skill to the product, which is a product-scope change.

**needs-decision (product scope):** the standalone Skills CLI route installs only skill folders, so no readiness script is present there. Options:
- (a) Accept that, and let the README say to run `ready --skills DIR` from a checkout or plugin copy.
- (b) Put the readiness script into a skill.

This choice is tied to the packaging question below. Recommendation: (a) for 0.3.

### What it reports

The command only reads files and runs `--version` probes. It has these sections:

- **Active Ruach:** the version and source of the copy that is running. The copy is found from `import.meta.dir`:
  - A snapshot: `ruach.json` version and revision, plus the local integrity result from `check` (no `--source`).
  - A source checkout: the `package.json` version, `git rev-parse HEAD` with `GIT_*` stripped and `--no-replace-objects` as in A1, and whether the tree is dirty.
  - A plugin directory: the `.claude-plugin/plugin.json` version and its path.

  The command reads only its own copy. It never parses Claude's internal plugin registry files.
- **Role and skill locations:** a read-only scan of known discovery roots, using only directories and frontmatter `name:` lines (no YAML dependency):
  - project `.agents/skills`, `.agents/agents` and `.claude/skills`;
  - user `~/.claude/skills`, `~/.agents/skills` and `$CODEX_HOME`/`~/.codex/skills`;
  - the plugin directory.

  For each Ruach skill and role it reports the version source and path. Duplicate names across locations are listed as warnings (input for Track C3). The Implementer must confirm the exact Skills CLI target paths for 1.7.0 and record them in the code as a short list.
- **Nested packages:** this covers each located executable skill, meaning one that has both `package.json` and `bun.lock`. For each dependency, it compares `node_modules/<dep>/package.json` `version` with the resolved version in the lockfile. The resulting state is `ready`, `missing`, `mismatched` or `no-dependencies`. It does **not** run `bun install --dry-run`, because Ruach does not guarantee that the command leaves the cache untouched. Each non-ready skill comes with the exact remediation command: `(cd DIR && bun install --frozen-lockfile)`.
- **Prerequisites:** `bun --version` and `git --version` are always checked. `herdr --version` and `HERDR_ENV` are checked for the Herdr route. `claude`/`codex` on PATH are informational. `just` is reported only for a source checkout. Probes run once with a short timeout, using the resolved absolute binary path in line with A6.

### Per-route verdicts

| Route | Ready when |
| --- | --- |
| `skill` (standalone skills) | Bun is present, and every located executable Ruach skill has `ready` nested packages. Duplicate Ruach skill names produce a warning, not a failure. |
| `native` (Claude plugin or snapshot roles) | Everything in `skill`, plus at least one Ruach role set is located (the plugin `agents/` or snapshot `agents/`), plus snapshot integrity passes when the copy is a snapshot. Missing `claude` is a warning. |
| `herdr` (coordinated) | Everything in `native`, plus Git, plus Herdr, plus `ruach-herdr` packages `ready`. Outside a Herdr session (`HERDR_ENV` unset), it reports `live launch needs a Herdr session` as a non-failing note, because readiness runs before a session is opened. |

Without `--route`, all three verdicts are printed and the exit code is 0. That form is informational.

### Read-only guarantee

The command never:
- creates, writes, renames or removes files;
- runs `bun install`, `claude plugin`, the Skills CLI or Git commands that modify state;
- writes global or project harness settings, or changes discovery links.

Remediation is printed, never applied. Paths under `$HOME` are shown as `~/…`.

### Output and exit codes

- **Default output:** short text, one section per heading, with lines prefixed `ok` / `warn` / `missing` and remediation commands.
- **`--json` output:** one object with these keys:
  - `schema_version: 1`
  - `active` (`kind`, `version`, `revision?`, `path`, `integrity?`)
  - `locations[]`
  - `packages[]`
  - `prerequisites[]`
  - `routes` (`{skill|native|herdr: {ready, missing[], warnings[]}}`)
- **Exit codes:**
  - 0: the requested route is ready, or no route was requested.
  - 1: the requested route is not ready.
  - 2: usage error.
  - 3: inspection itself failed, for example an unreadable location or an unexpected error.

### Tests

These go in `tests/ready.test.ts`. They run as a CLI from a foreign cwd with a temporary `HOME`, `CODEX_HOME` and a fake `PATH` holding stub `bun`/`git`/`herdr`/`claude` that log their arguments.

1. Read-only: a hash of the fake `HOME` and target (paths, contents, mtimes) is identical before and after every case, and the stubs saw only version probes.
2. Snapshot route: the reported version and revision match `ruach.json`. Drift makes `native` not ready, with exit 1.
3. Nested packages: a missing `node_modules` gives `missing` plus a remediation line. A wrong dependency version gives `mismatched`. A matching install gives `ready`.
4. A missing Bun, Git or Herdr is named under the correct route only. For example, missing Herdr fails `--route herdr` but not `--route skill`.
5. A Ruach skill duplicated across project and user locations produces a warning and does not change the exit code.
6. `--json` is stable: the keys and `schema_version` are present, and home paths are rendered with `~`.
7. Exit codes: an unknown option gives 2, an unreadable location gives 3, and no `--route` gives 0.
8. The command works from the source layout and from an installed snapshot copy after the source is removed, matching the existing installer pattern.

### Plugin-root vs per-skill packaging (product scope, needs-decision)

Not decided here. Today each executable skill has its own `package.json` and `bun.lock`, and the README says the plugin does not install nested packages. Before choosing between keeping per-skill packages, adding a plugin-root `package.json` (or workspace), or bundling skill scripts so they need no runtime dependencies, run these checks on a **clean** installed-plugin path. Use a fresh `HOME`, `claude plugin marketplace add <tag>` and `claude plugin install ruach@ruach`:

1. Where the plugin is cached, and whether the cache contains each skill's `package.json`, `bun.lock` and scripts unchanged.
2. Whether Claude runs any install or post-install step, and whether a root `package.json` affects plugin loading or installation.
3. Whether `bun install --frozen-lockfile` succeeds inside the cached skill directories, and whether the cache is writable.
4. Whether installed `node_modules` survive `claude plugin update` or a reinstall to a new tag, or whether the cache is replaced and the dependencies are silently lost.
5. Whether `ruach-handoff`'s validator and `ruach-herdr`'s `worker.ts --help` run from the cache with a foreign cwd after preparation.
6. The same checks for a Skills CLI copy, which receives only the skill folder, and for a snapshot, so the choice works across routes.
7. Disk size and the time for a first preparation, for each option.

Record the results in the Track E clean-install smoke evidence, then decide. The readiness command reports the nested-package state under any of these options, so it does not need to wait for this decision.

## Implementation boundaries

- A5 changes `scripts/install.ts` (install, check) and `tests/install.test.ts`, plus the README and `docs/operations.md` text for exit code 3 and interrupted-install recovery.
- C2 adds the `ready` subcommand, the `just ready` recipe, `tests/ready.test.ts` and documentation.
- Neither part adds package dependencies to the root tools.
- Neither part touches skill-local installers, the Skills CLI, the `claude plugin` commands or global settings.
- Neither part bumps versions or tags a release.
- Implement A5 before C2, because `ready` reuses `load`/`drift` and the interrupted-install signal.
