## Configuration preservation and visibility

Codex app-server `config/read` is used rather than manually approximating precedence from user TOML. Use the matching existing daemon when available, otherwise inspect with a short-lived native stdio process. Both read the actual requested cwd and unchanged environment; there is no manual/stripped settings substitute. Stdout exposes `config_reader` as daemon or stdio; `temporary_operations` notes possible native runtime initialization for stdio. Only relevant developer/skills fields are used in memory; raw response bodies are never logged.

Instruction text remains one native TOML argv override (`-c developer_instructions=<TOML string>`), preserving the default harness prompt. It is visible in native process arguments. Short argv also appears in the Herdr startup command; large argv instead travels through the private bootstrap described below. Redaction covers this launcher's own JSON and diagnostics, not native process inspection. Installed codex-cli 0.160.1 help lists TOML-parsed `-c, --config <key=value>` and no verified instruction-file, stdin or environment option. The bootstrap changes terminal transport; it emits no invented native file flag. Do not put secrets in canonical roles or preserved developer instructions. Existing skill entries and disabled unrelated skills remain intact. Worker overrides cover native/canonical workflow paths and aliases, both SKILL.md and folder representations. Public developer/skill payloads remain redacted.

Claude keeps normal user/project/native instructions and settings discovery. `--append-system-prompt-file` references the canonical role, while `--settings` merges a minimal overlay instead of copying user settings. Discovery scans repository, cwd ancestors, personal skills and accepted additional directories, using frontmatter names to recognize workflow aliases. Canonical technical skill directories are linked into private `.claude/skills` and exposed through `--add-dir`. Duplicate canonical names fail before temp creation. Account-synced caches, plugins, managed sources, legacy commands and linked-worktree fallback do not gate preparation. The launcher neither injects their bodies nor changes them. Existing nested project skill roots are scanned for targeted known-name suppression; account-synced caches are left to native discovery. Full catalog exclusion, including newly added entries after preparation, is unverified and not required by the role/instruction contract. Do not infer native catalog acceptance.

All temporary files remain private, reference canonical skill/role sources, and are never committed. Real Codex/Claude checks exercise resolution and effective argv preparation only. Fakes inspect generated settings and native argv; they do not emulate the entire native prompt or skill loader.

## Visibility limits and Codex reader investigation

The corrected contract requires only the Coordinator to load/execute workflow bodies, and prohibits launcher injection of workflow bodies into worker instructions. It does not require universal exclusion of workflow descriptions in native catalogs. Claude appends only the canonical role; known local workflow names receive the documented per-launch `skillOverrides` overlay. Coordinator overlays do not force disabled workflows on. Normal native customization discovery and its unrelated settings remain intact.

Installed Claude 2.1.289 has an account-synced cache. The [skills documentation](https://code.claude.com/docs/en/skills#override-skill-visibility-from-settings) excludes plugin skills from `skillOverrides`, and account inventories can change. Live account/plugin/managed/legacy catalogs and worktree fallback are therefore unverified visibility limits, not startup prohibitions. No `--bare`, `--safe-mode`, source restriction, slash-command disable, sync toggle or persistent cache movement is emitted. Fixture tests establish preparation and byte preservation, not live catalog acceptance.

## Codex runtime state and permission policy

Installed Codex 0.160.0 supports `app-server --listen stdio://`. The [official app-server contract](https://developers.openai.com/codex/app-server/) documents initialization and config/catalog reads independently from model turns. An isolated native probe sent initialize, initialized, config/read and skills/list only. It returned trusted project developer instructions, left pre-existing fixture config bytes unchanged and exited 0. It initialized state_5, goals_1, logs_2, memories_1 and queue_1 SQLite databases/WAL/SHM, installation_id, bundled `.system` skill files/marker and .tmp plugin-lock/git HEAD files. These runtime assets remained after exit; the probe tree was removed.

Authorized native preparation includes those documented runtime writes for the immediately following Codex launch; consumer assignments may restrict it. Accordingly, an absent, mismatched or unreadable daemon now triggers stdio inspection, with the actual layered configuration, cwd and environment. There is no replacement HOME/CODEX_HOME, guessed config, daemon installation, thread, turn or paid request. A ten-second inspection deadline kills a stalled reader; cleanup closes stdin and allows one second for exit before forced termination. The process is awaited on success and failure and is never left running. If both transports fail, preparation exits 3 with redacted diagnostics. Invalid config/catalog contents still fail their existing validation.

Normal resolve and start --dry-run may therefore initialize native runtime state. The launcher and inspection protocol do not write user config.toml, AGENTS.md, user-authored skills, profiles or credentials. Bundled native system skills may be initialized; these are separate from user-authored skill configuration. Native [configured database storage](https://developers.openai.com/codex/config-reference/) may place SQLite runtime assets outside the default CODEX_HOME. Only resolve --offline remains fully write-free. Existing daemon reads continue to be preferred; no shared daemon is stopped or replaced.

Portable `--permissions` defaults to inherit. Auto-review maps inside the Claude adapter to `--permission-mode auto`, verified by installed 2.1.289 help's permission-mode choices; the Codex adapter emits `--approve-for-me`, verified by 0.160.0 help's automatic-review/workspace-write description. Neither maps to bypass, dangerous full access or unconditional approval. Runtime help verifies the required flag before native config inspection. A request for auto-review on an adapter without a verified mapping fails exit 3 before mutation. Native permission flags conflict with auto-review and fail exit 2 before inspection; default inherit retains the existing bounded permission pass-through. Resolve/dry-run expose the policy, and offline selection records it without establishing capability. Real checks verify prepared flags, not native approval review during a model turn.

## Lifecycle and failure

Preflight verifies executables, installed help, Herdr kind support, authorized session context and unique live name. Default worktree placement checks a fresh destination and branch and resolves the base to a commit. Standalone launches (no usable launching workspace) use `git worktree add` followed by `herdr workspace create --cwd <worker-cwd> --label <name> --no-focus`, preserving caller PATH, HOME and already-set CODEX_HOME/CLAUDE_CONFIG_DIR through verified `--env`. When `HERDR_WORKSPACE_ID` names a workspace whose `herdr worktree list --workspace` repository key matches the source repository, the launcher instead runs `herdr worktree create --workspace <parent> --branch --base --path --label <name> --no-focus` (Herdr 0.9.0 verified: the result is `is_linked_worktree: true` and the checkout is listed by `herdr worktree list`), verifies the checkout identity, then splits the new workspace's root pane with `--env` because `worktree create` accepts none and its pane would otherwise inherit the Herdr server environment. The unused root shell pane remains. Responses use the installed API schema's `result.workspace.workspace_id`, `result.root_pane.pane_id` and `result.pane.pane_id`; IDs are never guessed. A failed or unconfirmed creation exits 4 as `worktree_uncertain`, retaining any checkout and branch. Tests use real temporary Git worktrees and fake Herdr/native CLIs. No live workspace or paid agent is started by these tests.

Native preparation runs again in the new checkout before startup. Dry-run inspects the source cwd and reports the planned checkout/base without creating it. An explicitly requested `--placement pane` additionally requires caller pane ID and layout, splitting right at width >=120 and down otherwise. Both modes preserve focus and forward configuration environment unchanged. Permission inheritance remains the default; explicit auto-review is mapped by the selected adapter. Help probes use `agent start --help`; they are distinct from the single mutating startup submission.

After preflight, adapters may need private material. Large native argv additionally needs a terminal bootstrap, including for Codex. Material uses the portable OS temp root or supplied existing directory, `ruach-herdr-` prefix, 0700 directories, 0600 data files, 0700 executable bootstrap and canonical symlinks where needed. Failure before workspace/split creation removes private material. Once worktree creation is attempted, a failure reports the path, branch and `worktree_state` and exits 4 without rollback. Once workspace/split creation is attempted, failures report `submission_state: unknown`, known workspace/pane IDs and retained private material.

The bootstrap avoids the observed Linux canonical-input loss at 4095 bytes. When conservatively quoted argv exceeds 3000 bytes, retain full arguments in `bootstrap/argv.json`. Shell initialization can prepend user executable paths, so an inherited private PATH prefix is insufficient and is no longer used. After initialization, `pane run` sources a private `setup.sh` that defines a POSIX shell function for the declared kind, pointing to the absolute private bootstrap. `pane wait-output --match ... --timeout ...` confirms a unique marker emitted only by that sourced file, not echoed command text. There is one initialization submission and then one intended native `agent start`; neither is retried. No startup file is disabled or edited, and other shell customization remains active. A shell that cannot establish the binding stays held before native submission.

The named `agent start --kind ... --pane ...` uses a short canonical command resolving to that private function. The script invokes the copied skill's Bun helper. It restores the explicitly forwarded environment (pinned PATH, config homes and adapter values) while retaining other startup environment, then uses `process.execve` on the probed absolute executable with exact prepared argv. Model/effort, permission flags, composed instructions and workflow overrides are unchanged. Argument data is never shell code. Short argv retains the direct path; OS/native argument-size limits still apply.

Before exec, the helper writes restrictive `executed.json` with a per-launch nonce, full payload SHA-256 and its process ID; exec failure removes only its own new receipt. A second invocation cannot overwrite a previous receipt. Before accepting ready or a matching native blocked state, the worker checks this receipt against the prepared payload and `pane process-info`: the expected pane, foreground group and process must match the helper's exec-preserved PID. Missing/mismatched evidence fails closed with `bootstrap_unconfirmed`, even if Herdr detects an unrelated default process as ready. The receipt establishes transport/process evidence, not a native thread identity or application acceptance. Never register its nonce/PID as a native session or infer role/permission acceptance from model defaults.

Large starts require Bun `process.execve`, verified `pane run`, `pane wait-output` and `pane process-info` capabilities, a POSIX-compatible shell binding and a setup command path short enough for safe terminal submission. Temp roots containing a PATH delimiter are now valid because PATH is not the dispatch mechanism. Source-cwd preflight checks available primitives/runtime/path before launch-space mutation; actual-cwd preparation is checked again before pane creation. Resolve/dry-run create no bootstrap. `temporary_directory` includes data, executable, setup and receipt; retain it after active or uncertain startup. The task-local shell binding remains with its pane until Coordinator release; no global shell or harness settings change.

A failed native readiness check triggers one read of the named agent. Only an exact name/kind/pane match with blocked state produces `action: awaiting-input`, exit 0 and `ready: false`; no dialog is answered, task sent or start repeated. Never retry, close a space automatically or remove material a submitted process may need. Successful or waiting startup retains private material and the worktree for Coordinator cleanup after reuse ends; retain committed work on its branch before removal. No prompt, monitoring loop, watcher, scheduler, eval or benchmark command is issued. Canonical-PTY regressions use harmless processes and do not establish actual native readiness or role acceptance; live source-wrapper launches remain a separate check.

## Pi and Goose

Updated 2026-10-24 against installed Pi 1.4.0 and Goose 1.56.0. Pi native preparation and its generated extension were checked with an isolated temporary HOME, synthetic offline provider and native resource loader: exact model catalog selection, extension loading, preservation of discovered `APPEND_SYSTEM.md` and `AGENTS.md`, and canonical technical-skill discovery passed. No model request was sent. Fixture tests exercise both roles, source resources, route selection, dry-run, configuration-root forwarding and failure gates for both adapters. A real Herdr worker launch and a Goose model turn were not run.

Pi preserves the native composed prompt using `before_agent_start`, rather than replacing discovered append instructions through CLI append flags. Its explicit `--skill` additions retain native discovery and configured disabled skills; the launcher omits canonical workflows for workers without claiming ambient workflow suppression. The generated extension reads only the canonical role body. Its prompt hook runs when an assignment is eventually submitted, after the launcher's readiness check.

Goose's additive `session --system` argument includes the canonical role and an index of canonical skill paths; skill bodies remain on demand. Its native settings, extensions, hints and skill discovery remain active. Worker indexes omit workflows, while Coordinator indexes include them. No selective native workflow deny interface is claimed. Role text is redacted in this launcher's results but visible in process arguments, including the Herdr submission. Never place secrets in canonical roles. `GOOSE_PATH_ROOT`, `GOOSE_MODE` and XDG roots, and Pi's configuration/session roots, are forwarded unchanged to the worker pane.

The installed Herdr advertises Pi but omits Goose. Goose remains a valid offline route and has tested native argv preparation, but live resolve, dry-run and start fail `unsupported_herdr_kind` (exit 3) until Herdr advertises that kind. There is no alternate kind, raw-pane substitution or model fallback. Pi and Goose support inherited permissions only. Goose has no portable explicit effort mapping; use `auto` in a routed profile.

## OpenCode v2

Updated 2026-10-23 against OpenCode 2.1.4, upstream tag `v2.1.4` at `68bc26b7da1990ce10ffecfbc1e09eb13aa5d824`. The previous v1 task-specific runner is not the v2 adapter. OpenCode v1 and future major versions remain gated.

The adapter starts an owned `opencode serve --stdio --port 0` reader with an ephemeral password. It reads `model.list` first because that v2 endpoint awaits plugin activation; direct agent/skill reads before activation can return empty catalogs. It then reads config, agents and skills for the selected cwd. Readers have a deadline, are closed after inspection and are forcibly reaped if needed. Preparation sends no model prompt, restarts no shared service, invokes no config patch API and does not read or copy credential files itself; the native CLI retains account ownership. Native runtime/log/database initialization can occur; only offline resolution guarantees no writes.

The selected native primary agent keeps its system text and permissions. An inline overlay adds the canonical role file to `instructions`, private canonical skill links to `skills`, and the explicit model to the agent and default config. Existing inline JSONC, instructions, technical-skill settings and unrelated fields are preserved. Other native config layers and managed settings still load. A second native read verifies the composed model, system preservation, role instruction path and worker workflow denies before creating worktrees or launch spaces. Managed settings that override these requirements fail with `opencode_config_conflict`.

Worker permissions deny `ruach-workflow-*` plus discovered workflow IDs and canonical aliases; the private skill root exposes only technical skills. Coordinators retain native workflow permissions and receive canonical workflow links without forced allows. This is targeted discovery, not protection against manually reading arbitrary files or later undeclared plugin changes.

Models use `provider/model`, including slash-separated model IDs. `#variant` and explicit effort must agree; an explicit effort must exist in the enabled model's native variant catalog. Omitted effort or `auto` uses the native default. A catalog entry does not establish account entitlement. There is no fallback. Only inherited native permissions are supported: OpenCode `--auto` approves requests without an approval reviewer and cannot implement Ruach `auto-review`.

The worker starts as `opencode --standalone`, with the selected OpenCode/XDG configuration environment passed to its pane. Its startup settings are isolated from the shared service. Inline settings are withheld from launcher output but remain visible to the local native process and Herdr environment transport. The adapter does not copy credentials or write user settings. Private context and skill links remain with the launch until the caller releases it.

Verification includes the fake-CLI contract suite and the reproducible [native transport smoke](../../../evals/ruach-opencode/README.md). The latter uses real OpenCode 2.1.4, an isolated HOME/XDG/config root and a provider policy allowing only an ephemeral loopback model. Implementer and Coordinator both delivered the full canonical role plus ambient instructions and completed; native technical-skill discovery and differing workflow permissions were checked. Four local fixture requests, zero paid requests. This establishes transport/configuration behavior, not model reasoning quality or a real consumer task.
