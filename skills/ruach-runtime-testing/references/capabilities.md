# Capabilities and observation limits

Use before assigning meaning to runtime evidence. Record each required capability as available, blocked or unverified with an actual probe/reference, tool/version, environment and scope.

| Capability | What it can establish |
| --- | --- |
| Browser DOM/input | Actual inspected document and performed browser interactions on an identified build |
| Desktop window/input | Actual application/window interactions on the named platform |
| Screenshot/video | Captured visible state/motion at the stated times; not unperformed interaction |
| Logs or trace | The recorded event or measured boundary; not the whole user experience |
| Audio playback | Actual playback route/action; not necessarily capture or listening |
| Audio capture | Recorded output at the named tap/device, with routing/format; not proof anyone heard it |
| Listening | Actual observer and playback/listening route, conditions, input and attributed judgment |

Reading audio code, generating a waveform or seeing scheduled events is not hearing playback. Capture at an internal bus does not establish sound at the output device. Reading someone else's playback record is replay evidence; retain the observer's attribution rather than claiming personal execution. A valid actual listening observation can support its stated goal without proving every audio property.

Keep evidence classes separate when capabilities differ. An unavailable required experience holds that goal; a useful source check or screenshot does not replace it. Record capability or permission failure as observed, without guessing a product cause or silently switching tools/routes.

Consumer policy determines privacy, redaction and retention. Preserve original raw evidence in its permitted location; commit only authorized sanitized artifacts. Name resource owner, initial state/digest, allowed writes, retention and release conditions. Do not overwrite originals or delete evidence to make a retest appear clean.
